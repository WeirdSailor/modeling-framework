Drafts: proposed architecture in diagrams

A visual companion to Docs/drafts-architecture.md. Each diagram answers one question. The written document has the detail, the decisions (D1–D28), the resolved conflicts (C1–C14) and the items still open (C15–C17).

Releases: Phase 1 (day one) = one private sandbox per operator with the full committed-plan design · Phase 2 = multiple drafts and comparison · Phase 3 = sharing.

Colour key: blue = core design, built in Phase 1, orange / purple = open drafts (dotted lines), red = a limitation or a rejected path.

0. Overview: one architecture, two stages

The same architecture serves Phase 1 and the target. Blue parts are built properly in Phase 1 and don't change later. Only the dashed parts grow: one scenario becomes many, and one sandbox becomes many shared drafts. Facts, scenario input values and global policy arrive separately and only meet in the baseline calculation. Arrows show the direction data flows. Two heads mean both ways.

1. Proposed components and who talks to whom

The same calculation library (blue) runs in both the browser and the server, so both always produce the same numbers.

2. Inside a draft: one draft, many units

A unit does not get its own draft. A draft is a container, and each unit added to it becomes one action (one row) with its own window, output and reasons.

3. Open decision D14: how each unit contributes

Both options add units up to get the draft's impact. They differ in the shape of each unit's contribution over time. Below is the same draft, with the same three units and windows, drawn both ways. This is still to be decided.

4. How the dotted line works: one data set, many drafts

The heavy data is stored once. A draft is just a short list of units and times, drawn as the stored baseline plus that draft's extra units.

5. Day one: the sandbox

Each operator has one private, saved working area. Add units, see the dotted lines, commit all or some, carry on. A sandbox is an ordinary draft with restrictions (one per user, private), so Phase 2 lifts a rule rather than rebuilding.

6. Comparing options across all areas (Phase 2)

Dotted lines show one area at a time. The comparison table puts competing drafts side by side across every area, plus a read-only "A + B" preview of two drafts together. Both arrive in Phase 2 with multiple drafts. Day one has the pin instead.

7. What happens when an operator commits

One transaction: hard time rule, warnings to acknowledge, close the loaded plan actions (if this is an edit), add the new plan actions, and let the database reject any overlap. Then every screen is told.

8. Draft lifecycle: committed drafts never become editable again

"Edit" on a committed draft loads it into your sandbox, with a warning if the sandbox isn't empty. The original stays in the plan until you commit, and then the edited version replaces it in one step.

9. Editing a committed draft: supersede, with no gap and the past kept

Example: at 16:10 an operator trims DRAXX-1 (committed 15:00–19:00) to finish at 18:00. Each row is a plan version.

10. Sharing: who sees what (Phase 3)

Real users on different machines, with every rule checked by the server.

11. Data model: drafts hold intent, plan actions hold the record

The sandbox is a row in drafts (kind = sandbox). On commit, actions become immutable plan_actions under a new commitment record. Demand and requirement values move into scenario tables, reserve % and requirement rules into global planning policy, and contracted / constrained values into global availability data: facts, input values and policy are kept apart.

12. Scenarios (future): the same drafts, tested against different futures

Drafts vary what we do. Scenarios vary what the world does (demand, wind, solar, requirements). Because drafts store intent, any draft can be evaluated against any scenario unchanged. Phase 1 builds only the seams, with one central scenario.

13. Delivery phases

Phase 1 is the day-one release: the sandbox with the full committed-plan design. Multiple drafts (with comparison) come before sharing, because comparing options matters more to operators than sharing them.
